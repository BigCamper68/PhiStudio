# 1.0.9 checkpoint 11

Version code 106; base checkpoint 10 (`1c0df7ce369597c7f2e8850175999883747dc6e1`).

## Compatible noise-field export precision

The earlier 0.03-pixel figure described a measured difference between rectangle
corners after converting native noise animation to Phira-Pro Line2Area tracks.
Its unit is a pixel of the virtual 1350x900 RPE canvas, not a percentage or a
whole physical display pixel. Native project coordinates are retained unchanged.

The old baker allowed 0.025 canvas pixels per channel and associated an f32
sampled transform with the original f64 sample time. The new baker aligns knot
times with the native f32 clock, inserts native easing-table slope changes and
uses a 0.0005-pixel curve budget plus an explicit arithmetic rounding allowance.
The budget is a refinement criterion, not a universal final-corner error bound.
Final corners and RPE interpolation are checked independently.

The rounding allowance prevents f32 arithmetic noise from producing millions of
redundant events. The existing 2,000,000-evaluation limit is retained. Legacy
checkpoint 9 track reconstruction uses the original baker profile, so saved
projects with the old empty-timeline bug still recover correctly.

The dense MULTIPHEX comparison has 7,407 samples (2,400 per second plus lifetime
boundaries). With f32 RPE endpoint conversion and interpolation, checkpoint 10's
maximum observed corner difference is 0.031995 canvas pixels; checkpoint 11's is
0.00513, about 6.2 times smaller. This is a measured result for this chart at 3:2,
not a promise of zero error or of the same bound for every chart and viewport.

Bit-identical continuous playback across players is not guaranteed: native
animation first rounds the clock to f32, whereas Phira-Pro uses f64 keyframe
times and f32 interpolation and transforms. At fast rotations, the native time
steps alone move the corner by a few thousandths of a canvas pixel. More dense
linear approximation cannot remove this difference at every possible time.
The different aspect projection of native and RPE fields is unchanged.

Reference: the released Phira-Pro
[animation clock/interpolation](https://github.com/Phira-Pro/Phira-Pro/blob/v0.8.2-pro.16/prpr/src/core/anim.rs),
RPE parser, marker geometry and f32 tween implementation. Rust checks compile
the actual marker/transform methods with minimal vector/constant-animation
shims; they are not a complete external-player or physical-device run.

## Noise Field controls

- Area, Move, Scale and Rotate have at least 64 dp of width and wider padding.
- Previous/next key buttons have at least 48 dp; + Key and Copy at least 72 dp.
- The bottom navigation starts with the field-list button, then previous and
  next field. The list is 120 dp wide with ellipsis for long names; both arrows
  share the remaining space equally instead of their former 34 dp width.
- Existing control styles, 32 dp form-button height, 34 dp footer, timeline,
  gestures, mode/Menu buttons, autosave and Undo/Redo are retained.

## Verification

The synthetic fast-rotation/zero-scale-growth regression and supplied MULTIPHEX
now require corner error below 0.01 canvas pixels. The complete 160-field
Desultory color export still fits the existing animation budget. Android 8/14
Robolectric regressions cover the issued checkpoint 9 ZIP, saved old projects,
ordinary color export, native timeline blocks, Undo/Redo and workspace reload.
The existing UI suite checks common layout, buttons, gestures and footer bounds.
Actual delivered ZIPs are checked for audio/asset preservation and reimport.

Use the fixture environment variables documented for checkpoint 10. The host
`NoiseFieldExportProbe` accepts an optional sample-rate argument (default 240 Hz;
precision validation uses 2400 Hz). Reports distinguish current validation from
retained GPU reports for unchanged renderer/shader sources. The ARM64 profile
continues to state its native-graphics exclusions and unavailable chart fixtures.
